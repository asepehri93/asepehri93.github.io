Technical brief · engineering & hiring

Dream interpretation engine

Summary of system design, rigor, and design tradeoffs at a level appropriate for technical evaluation and planning. This is not a build specification; implementation detail lives in the product repository.

System summary

The engine is a server-orchestrated, multi-stage analysis pipeline combining large language models with structured methodology, retrieval-augmented context, and explicit safety and epistemic guardrails. It powers Dream Work in the SkyLune iOS client: users progress through a guided flow (dream text, emotional scenes, personal associations) and receive multi-hypothesis interpretations and integration-oriented outputs instead of a single dictionary-style answer.

The methodology aims to reflect depth-oriented clinical craft—personal meaning first, provisional language, multiple defensible readings—while remaining deployable software with defined session lifecycle, API boundaries, and degradable dependencies.

Architecture

Orchestrated multi-agent workflow. Analysis is not a one-shot prompt. A central orchestrator advances a discrete session through ordered stages aligned with how structured dream work is practiced: stabilize narrative, attend to feeling-tone, anchor symbols in the dreamer’s associations, then introduce curated conceptual material as support rather than authority. Specialized agents own slices of the pipeline (intake/structure, affect, associations, pattern detection, interpretation synthesis, optional amplification, integration planning, quality review, narrative summary). Each stage exposes a narrow I/O contract in structured form to keep behavior testable, auditable, and evolvable without a monolithic rewrite.

Dual retrieval (“dual-RAG”). Semantic retrieval spans multiple curated channels—conceptual material, exemplar cases, procedural guidance—so generation is grounded in an internal library aligned with the chosen methodology, not only in pretrained model prior. Retrieval is selective: it informs hypotheses and framing without collapsing output into generic archetype talk. Knowledge bases, orchestration policy, and generation are intentionally separated.

Methodology and policy layer. Interpretation is constrained by injected axioms and policies (e.g., multiple valid interpretations, non-diagnostic stance, disciplined use of archetypal vocabulary). This layer encodes product ethics as well as architecture: the system avoids false certainty and privileges the user’s own material.

Design differentiators

  • Epistemic design: Shipping several hypotheses plus integration steps is implemented as data structures and UI contracts, not only product copy.
  • Associations as first-class inputs: User-supplied associations drive interpretation before archetypal amplification dominates—inverted relative to typical consumer “AI dream” products.
  • Parameterized depth: Analysis depth (e.g., symbol count, optional amplification) maps product tiers to compute and retrieval cost without unrelated code forks.
  • Constrained generation: Output stays within retrieve-then-reason boundaries rather than unconstrained storytelling.

Client integration

The iOS app maintains a local-first session artifact synchronized with the engine over HTTPS. The client implements extended timeouts for LLM-heavy steps, graceful degradation under slow network or server load, and schema-level compatibility across Swift and Python stacks—standard distributed-systems practice applied to a multi-screen flow rather than a single form post.

Scope of this overview

This page does not include full state diagrams, prompt libraries, knowledge-base contents, embedding indices, or reproduction procedures; those remain internal engineering artifacts. Implementation documentation (API routes, agent contracts, setup) and deployment context live in the repository’s dream_engine/docs/ tree and deployment notes.

Positioning: a methodology-first, retrieval-grounded, multi-agent dream analysis engine built for accountable LLM use in a consumer ritual product—designed for depth, epistemic humility, and operability rather than black-box one-shot answers.

Literature Review Engine

Dual-RAG MAS Engine · research workspace for ingestion, retrieval, analysis, and collaboration

Literature Review Engine is a web application built to turn paper collections into usable project knowledge. Instead of acting like a thin chat layer over uploaded documents, it organizes papers, figures, artifacts, and question answering around a shared namespace so the workflow feels like a real research workspace.

The current product supports paper upload, hierarchical ingestion and retrieval, figure extraction and analysis, artifact browsing, source-aware question answering, and namespace sharing. The result is a system that helps teams move from raw documents to structured, reusable project context.

Feature 01

Paper upload and namespace ingestion

Papers are uploaded into project-specific namespaces through a web workflow that emphasizes organization and control. Users choose the target workspace, add files, and trigger ingestion so the content is prepared for retrieval, figure handling, and downstream analysis.

That structure matters because it turns document intake into an operational step rather than a one-off experiment. The product starts from project context, not from loose files.

Feature 02

Hierarchical retrieval and source-aware question answering

The core retrieval design preserves document structure instead of flattening papers into disconnected chunks. In practice, that leads to stronger section-aware retrieval and more coherent answers for methods, results, and paper-specific questions.

For users, this shows up as a question answering experience that feels better grounded: answers are tied back to retrieved paper context rather than produced as generic summaries.

Feature 03

Figures and artifacts as first-class project assets

The system does more than index text. It can extract figures during ingestion, surface them inside the interface, and support figure-level analysis so visual evidence becomes easier to inspect and reuse.

Alongside papers, each namespace can also track artifacts such as datasets, models, force fields, or related project files. That makes the workspace more useful for real technical teams that need both documents and supporting assets in the same environment.

Feature 04

Shared project knowledge

Namespaces are designed to be collaborative rather than single-user. Sharing controls make it possible to hand off project spaces and related resources to teammates, which is important for research groups and technical teams that work across shared paper sets.

This product direction is deliberate: the goal is not just better retrieval, but a workspace where project knowledge can be organized, revisited, and discussed together.

Technical brief · engineering & hiring

Dual-RAG MAS Engine

A technical overview of the architecture, system boundaries, and engineering decisions behind the research workspace. This complements the user-facing product page rather than replacing implementation documentation.

System summary

The engine is a full-stack research application I designed and implemented to turn technical paper collections into project-scoped knowledge systems. It combines a web interface, an application programming interface layer, namespace-based retrieval, a graph-backed knowledge layer, and multi-agent orchestration for question answering and analysis.

The project is designed to show applied artificial intelligence engineering beyond prompt wiring: system design, retrieval quality, observability, workflow boundaries, failure handling, and the balance between deterministic software and language-model reasoning.

Architecture

  • Frontend: Next.js interface for authentication, namespaces, ingestion, figures, artifacts, reports, and question answering.
  • Backend: FastAPI service exposing deterministic administrative routes and language-model-powered research routes.
  • Retrieval: namespace-scoped vector storage paired with graph-backed context retrieval for broader relationships.
  • Orchestration: LangGraph workflows with explicit agent roles for planning, retrieval, writing, and quality checks.
  • Storage: application data plus file-backed research assets designed for growth beyond a notebook prototype.

Notable design choices

  • Hierarchical retrieval instead of flat chunks: preserves parent-child document structure and improves section-aware evidence assembly.
  • Deterministic versus language-model boundaries: namespaces, uploads, listings, and administration stay predictable; synthesis is used where it adds value.
  • Figure-aware knowledge handling: extracted figures can be surfaced and analyzed rather than remaining trapped inside portable document files.
  • Artifact-aware project organization: namespaces can hold project-relevant assets alongside the papers that describe them.
  • Observability and diagnostics: timing logs, correlation identifiers, and failure analysis make multi-stage system behavior easier to debug.

Industry relevance

From an industry perspective, the project demonstrates end-to-end ownership across product and engineering concerns: web delivery, backend design, retrieval systems, multi-agent orchestration, quality instrumentation, and the practical judgment to decide when language-model logic should and should not be in the loop.

It is also a concrete example of how to design around workflow rather than around isolated model calls. The product surface, the system boundaries, and the observability strategy are all part of the engineering work.

Roadmap direction

  • Structured table ingestion and retrieval for stronger numeric evidence handling.
  • Long-form review generation and report storage across paper sets.
  • Claim-layer evidence tables for agreement, disagreement, and gap detection.
  • Cluster-aware routing for larger namespaces.
  • Richer multimodal handling across figures, tables, and diagrams.
  • Stronger collaboration and project-sharing workflows as the workspace matures.

Positioning: a research workspace that combines structured ingestion, hierarchical retrieval, figure-aware analysis, and multi-agent reasoning in a product built for actual technical workflows.
